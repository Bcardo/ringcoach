# Exercise-specific next-time proposals (#69)

The existing coaching response may include up to four short next-time notes. Training shows each under its matching exercise, beside the dated saved reference and latest confirmed performance. The user still chooses the workout. Notes never complete work, advance a rotation, or edit the plan.

`coach-v18-exercise-followups` adds an optional `exercise_notes` response field only when eligible baseline references exist. Each request uses compact `eN` references. Storage converts these to a versioned digest of the exact baseline, saved routine/instructions, and latest confirmed completed/partial performance and provenance. No extra routine model call, screen-level inference, schema migration, or recognition change is introduced. Empty legacy three-section responses remain readable; malformed optional notes are discarded independently of the main response.

Matching is conservative: exact unique exercise name across the saved baseline, all latest-date sets, no future or planned performance, and a latest performance within 14 calendar dates including the request date. Ambiguous names receive no note. A changed reference, routine, instruction, correction or new same-exercise performance hides an incompatible proposal. An intervening different exercise or diet-only update does not invalidate it. Training scans only advice JSON from the latest 120 cards within the same 14-date window; no large context snapshots or network calls on refresh. This bounded window may omit an older otherwise compatible note. A missing note leaves the existing reference/performance visible.

The prompt requires conditional suggestions grounded in saved rules and confirmed evidence. It forbids invented numerical loads without effort/completion/increment/load-convention evidence, automatic workout selection, and carrying today's fatigue assessment into a later session. The UI labels notes as dated suggestions. These are **model proposals**, not a deterministic progression calculation: reference identity and staleness are checked locally; numerical and semantic correctness are not mechanically proved. An explicit training preference should produce a replacement note through the normal coaching response. A failed or empty response cannot establish that a prior proposal has incorporated that preference; dated notes and current pending/retry status remain visible. A full structured rule/withdrawal engine remains separate work under #69.

Existing cards are not regenerated or retrospectively assigned notes. New notes appear after a subsequent normal workout report/question with sufficient matching evidence. Existing general training feedback remains at the top of Training.

Tests cover compact schema references, input immutability, legacy and malformed optional payloads, corrections/plan changes, ambiguity, old/future/planned performance, diet/day stability, and request accounting. The seven full production-prompt corpus cases now include an eligible exercise and response-schema overhead. Provider diagnostics contain fixed case/status flags, counts, bytes and latency only; no owner facts, saved cards or response text.
