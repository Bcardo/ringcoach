# Training feedback rather than a completed-workout recap

`coach-v17-training-feedback` changes the training-output instructions, not the response schema, model, context-selection/packing contract, recognition, saved plan or call graph. The previous instruction required the coach to enumerate the applicable training day, exercises, known sets/repetitions/weights and adjustments; the Training table already displays those facts. That instruction is a concrete source of the overlap reported by the owner. No private owner response was copied into fixtures or public tracking.

The revised training section prioritizes the current question, an evidence-backed assessment, an actionable next step and a short reason (normally one to three items). After a completed workout, any recommendation concerns the next occurrence of that workout type, with flexible user selection of training day. It does not reschedule completed work for today or advance a rotation by calendar date. Keeping the saved plan with a useful observation can be appropriate; new weights, cuts, technique judgments or RPE are not invented to make every update sound different. Numerical progression still needs the saved rule, completion/effort evidence and weight conventions. A diet-only update can keep training continuity briefly while diet addresses the new intake. Explicit requests to recall performance still get the relevant facts.

Historical cards remain attributed to their original prompt/version. This affects subsequently generated responses; installation does not regenerate an owner's card, replay completed recognition or alter workout/nutrition facts. No new routine model call or automatic refresh pipeline is added. The existing daily-focus panel consumes the same training field. Broader next-time progression/contributor implementation remains #69/#35; this prompt change does not finish those issues.

## Comparison and limits

An opted-in Android test loads the candidate prompt from the test APK so it can run before replacing the main app. It reconstructs the prior training instructions for a baseline and uses entirely synthetic contexts with the same Qwen model/request schema/output budget. Five cases, two arms, ten provider calls: completed multi-exercise update; explicitly supported next-time progression; partial work with reported fatigue; diet-only update; explicit recorded-number recall. The saved credential is read only for the connection; no owner facts, cards or model responses are read/saved/logged. Reports contain fixed case/arm/pass/status/byte/time fields.

One run completed ten calls with zero transport/decode failures. The prior prompt passed four of five finite spot checks, failing the completed-update recap check; the new prompt passed five of five. Gates check limited observable behavior (forward-looking text, avoiding a full three-load recap, supported target, avoiding that target in the partial case, brief diet-only continuity, and retained explicit recall). They do not prove all future responses are non-repetitive, all suggestions are good, all unsupported claims are absent, or broad quality superiority. No LLM judge, response archive or owner-data experiment is introduced. Source evidence and normal-use feedback remain necessary.

## Request budget

The source prompt grows by 576 UTF-8 bytes. Hard cap stays 131,072 bytes and soft target 114,688. Packaging tests now exercise both the original short synthetic system prompt and the full production prompt, preserving every mandatory sample/source record and accounting for actual serialization. The short-prompt benchmarks alone did not establish full production-prompt headroom; this change makes that boundary explicit.

With the new full prompt, seven fixed synthetic variants fit the hard cap: question 25,846 bytes; mixed 103,609; correction 103,719; morning 103,584; retained 28,128; long plans 121,614; full history 101,754. The long-plan case exceeds the soft target and retains mandatory evidence, as designed. These are finite synthetic sizes, not a universal maximum or a replay of the original failed owner's payload.

Normal/test builds, 114 JVM tests and lint pass before installation; live comparison passed through the required no-restart wrapper. Installation and data/reader preservation are recorded in the PR/issue update. This changes the content-generation policy, unlike the earlier UI-only boundaries; synthetic success is not normal-use reliability acceptance or a #50 personal pilot.
